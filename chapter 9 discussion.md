# Chapter 9 Discussion — Question 1

Explain how creating and using classes supports Object Oriented Programming and S.O.L.I.D. design principles, give specific examples

The easiest way I can explain this is with a car. If I was writing a program about cars without classes, I'd end up with a bunch of loose variables like car1_make, car1_model, car2_make for example. Plus functions scattered everywhere that work on them. A Car class fixes that. I can give it attributes like make, model, and fue level, and methods like drive() and refuel(), so everything about a car lives in one spot. That's what OOP is built on. It also gives you encapsulation, since the object manages its own data instead of letting the rest of the program change it however it wants. Classes are also what make the SOLID principles work in practice. Single Responsibility means my Car class should only deal with car behavior. If I'm building a dealership program, the payment logic goes in a separate Sale class, not inside Car. Open/Closed comes in when I want something new, like a SportsCar with a launch_control() method. I can just make SportsCar inherit from Car rather than editing the original class. Liskov Substitution follows from that: anywhere my code expects a Car, a SportsCar should work fine without causing errors. The last two took me a little longer to understand. Interface Segregation basically says don't force a class to include methods it doesn't need. A Car shouldn't have to implement fly() or sail() just because some giant Vehicle interface includes them. Dependency Inversion means classes should rely on general types instead of specific ones. If Sale depends on a general PaymentMethod, I could switch from cash to credit card without rewriting Sale. Overall, classes keep code organized, and following these principles means when something changes, it only breaks in one place instead of five.
